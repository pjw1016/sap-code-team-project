## 1. 프로그램 목적

이 프로그램은 MM RFQ를 기준으로 공급업체별 견적(MQ)을 비교하고, RFQ Item 단위로 거래선을 채택하거나 채택취소하는 SAP Fiori/UI5 프로그램이다.

업무 흐름은 다음과 같다.

1. 조회조건으로 RFQ Header를 조회한다.
2. RFQ Header 목록과 상태별 KPI를 확인한다.
3. RFQ Header를 선택하면 Mid Column에서 RFQ Item 목록, 금액 비교 차트, MQ 비교 목록을 확인한다.
4. RFQ Item별 MQ 후보를 비교한다.
5. 선택 가능한 MQ를 채택하거나 기존 채택 MQ를 채택취소한다.

## 4. Backend/OData 전제

### 4.1 메인 OData Service

메인 업무 서비스는 `ZGWD3MM0005_SRV` 기준으로 개발되었다.

| EntitySet | 용도 |
|---|---|
| `RFQHeaderSet` | RFQ Header 목록, KPI 계산용 상태/건수 조회 |
| `RFQItemSet` | 선택 RFQ의 Item 목록 조회 |
| `MQCompareSet` | 선택 RFQ Item의 MQ 후보 비교 조회 |
| `MQDetailSet` | MQ 상세 Dialog 단건 조회 |
| `QuotationItemSet` | MQ 채택/채택취소 Update 처리 |

### 4.2 채택/취소 처리

`QuotationItemSet`은 `MqNo`, `MqItem`을 Key로 사용한다.

| ActionType | 의미 |
|---|---|
| `AWARD` | 선택 MQ를 RFQ Item의 최종 거래선으로 채택 |
| `CANCEL` | 현재 채택 MQ의 채택 상태 해제 |

Backend 주요 업무 규칙:

- 미응답 MQ는 채택할 수 없다.
- 이미 PO가 생성된 RFQ Item은 채택/채택취소할 수 없다.
- 하나의 RFQ Item에는 하나의 MQ만 채택되어야 한다.
- 채택 시 같은 RFQ Item의 기존 채택 MQ는 Backend에서 해제한다.

RFQ Header Table 컬럼:

| 2 | 문서일자 |

- 조회조건의 MQ 번호 필터 기능은 Header Table 컬럼 제거와 무관하게 유지된다.
- `회사코드`, `구매조직`, `구매그룹`은 덜 중요한 컬럼이므로 반응형 pop-in 대상이다.

### 7.2 Mid Column - RFQ Item 목록

RFQ Item Table 컬럼:

| 순서 | 컬럼 |
|---|---|
| 1 | RFQ Item |
| 2 | 자재코드 |
| 3 | 요청수량 |
| 4 | 납기일 |
| 5 | 채택상태 |
| 6 | 채택 공급업체 |
| 7 | 플랜트코드 |
| 8 | 저장위치코드 |

참고:

- 자재코드는 자재명과 함께 표시한다.
- 플랜트코드는 플랜트명과 함께 표시한다.
- 저장위치코드는 저장위치명과 함께 표시한다.
- 상태는 `PO생성`, `채택`, `미채택` 3종으로 본다.
- `PO생성`, `채택`은 Success 계열, `미채택`은 Error 계열로 표시한다.
- Row Highlight도 상태 기준으로 표시한다.

### 7.3 Mid Column - MQ 비교 목록

MQ 비교 목록은 `sap.ui.table.Table`이다.

주요 컬럼:

- MQ 선택
- MQ 상세조회
- MM견적(MQ)번호
- 공급업체코드
- 자재코드
- 견적수량
- 가격단위
- 단가
- 적용환율
- KRW 환산총액
- 납기일
- 추천여부
- 선택가능여부

참고:

- 공급업체코드 컬럼은 공급업체명과 함께 표시한다.
- 자재코드 컬럼은 자재명과 함께 표시한다.
- 금액 비교 차트는 현재 MQ 비교 데이터 기준으로 생성된다.
- 같은 공급업체의 MQ가 여러 건이면 차트 축이 공급업체 기준이라 1개 막대로 보일 수 있다. 이는 샘플 데이터 또는 차트 표현 기준의 문제이며, 현재 로직상 오류로 보지는 않는다.

## 8. 개발 중 확정한 판단

| 주제 | 확정 내용 |
|---|---|
| CSS 사용 | 최대한 사용하지 않고 UI5 표준 컨트롤/상태를 사용한다. |
| 상태 색상 | CSS로 임의 색상을 넣지 않고 `ObjectStatus` state 등 UI5 표준 색상을 사용한다. |
| 일부채택 KPI 색상 | UI5 표준 Warning/주황 계열을 그대로 사용한다. |
| Search Help 방식 | 납기지연 프로그램처럼 `TableSelectDialog` 공통 로직을 사용한다. |
| 오류 표시 | Toast가 아니라 `MessagePopover` 중심으로 조회조건 오류를 표시한다. |
| RFQ/MQ 날짜 검색 | RFQ/MQ Search Help에서 날짜는 표시만 하고 검색 필드에서는 제외한다. Gateway에서 날짜 타입에 `Contains`를 걸면 오류 가능성이 있기 때문이다. |
| RFQ Header MQ 수 컬럼 | 응답 공급업체 수와 중복성이 있어 제거했다. 단, MQ 번호 조회조건은 유지한다. |

| 3 | 1차 개발 완료 태그 또는 별도 백업 여부 결정 | 선택 사항 |

### 11.2 2차 개발 준비

2차 개발의 핵심은 PO 생성 기능이다.

| 단계 | 할 일 | 설명 |
|---|---|---|
| 1 | PO 생성 기능 설계서 작성 | 버튼 위치, 생성 조건, 성공/실패 UX 정의 |
| 2 | Backend OData 확장 방식 결정 | Entity Update, Function Import, Action성 Entity 중 선택 |
| 3 | SEGW/MPC/DPC 확장 | PO 생성용 EntitySet 또는 Function Import 구현 |
| 4 | Backend 업무 규칙 확정 | 채택 MQ만 PO 생성 가능, 이미 PO 생성 시 차단 등 |
| 5 | UI5 PO 생성 버튼 구현 | RFQ Item 또는 MQ 기준 버튼 위치 결정 |
| 6 | PO 생성 성공 후 화면 갱신 | Header/Item/MQ 상태 재조회 |
| 7 | 오류 처리 | OData Business Exception을 MessagePopover/MessageBox로 표시 |
| 8 | 회귀 테스트 | 채택/취소/Search Help/PO 생성 간 충돌 확인 |

### 11.3 PO 생성 기능 설계 시 확인할 질문

| 질문 | 확인 필요 이유 |
|---|---|
| PO 생성은 RFQ Header 단위인가, RFQ Item 단위인가? | 버튼 위치와 Backend 처리 단위가 달라진다. |
| 부분채택 RFQ도 PO 생성 가능한가? | 일부 Item만 PO 생성할지 정책이 필요하다. |
| PO 생성 후 채택취소를 완전히 막을 것인가? | 현재 Backend는 PO 생성 후 채택 변경을 차단하는 방향이다. |
| PO 생성 성공 시 PO 번호를 어디에 표시할 것인가? | Header/Item/MQ 목록 컬럼 또는 Dialog 필요 여부 결정 |
| PO 생성은 동기 처리인가, 생성 후 결과 조회인가? | UI Busy 처리와 오류 처리 방식이 달라진다. |
| PO 생성 대상 MQ의 공급업체가 여러 개인 경우 분리 생성할 것인가? | MM 구매오더 Header는 공급업체 기준이므로 중요하다. |
