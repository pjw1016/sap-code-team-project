# [MM] 견적 비교 및 거래선 채택 인수인계서 - 2차 개발 API 전환 정리

## 1. 문서 목적

이 문서는 `[MM] 견적 비교 및 거래선 채택` Fiori 프로그램의 2차 개발을 학원 환경에서 이어가기 위해 작성한 인수인계서이다.

현재까지 2차 개발 설계서 V1.0.0은 `Function Import + EXECUTE_ACTION` 방식으로 작성되었으나, SAP Gateway Client 테스트 결과 현재 시스템에서는 해당 방식이 URI Parser 단계에서 안정적으로 동작하지 않았다.

따라서 학원에서는 기존 V1.0.0 설계서를 그대로 구현하지 말고, 본 문서의 판단 근거를 바탕으로 **2차 개발 설계서 V1.1.0에서 PO 생성 API 방식을 `PoCreateRequestSet + CREATE_ENTITY` 방식으로 전환**하는 것을 권장한다.

## 4. 2차 개발 V1.0.0 설계 요약

2차 개발 설계서 V1.0.0에서는 다음 방식으로 설계하였다.

| 항목 | V1.0.0 설계 |
|---|---|
| API 방식 | Function Import |
| Function Import Name | `CreatePoFromRfq` |
| 입력 파라미터 | `RfqNo` |
| 반환 Entity Type | `PoCreateResult` |
| 반환 EntitySet | `PoCreateResultSet` |
| 처리 메소드 | `/IWBEP/IF_MGW_APPL_SRV_RUNTIME~EXECUTE_ACTION` |
| UI5 호출 예정 방식 | `oModel.callFunction(...)` |

업무 로직 자체는 유지한다.

- UI5는 RFQ 번호만 Backend에 전달한다.
- Backend가 채택 MQ Item을 조회한다.
- Backend가 공급업체/조직/통화/지급조건 기준으로 PO Header를 그룹핑한다.
- SNRO 번호 오브젝트 `ZNRD3MM01`로 PO 번호를 채번한다.
- `ZTD3MM0016`에 PO Header를 생성한다.
- `ZTD3MM0017`에 PO Item을 생성한다.
- PR 참조 정보를 갱신한다.
- 저장 정책은 All-or-Nothing으로 처리한다.

## 6. DPC_EXT에 작성한 현재 코드 상태

현재 `ZCL_ZGWD3MM0005_DPC_EXT`에는 Function Import 테스트를 위해 아래 메소드가 재정의되어 있다.

```abap
/iwbep/if_mgw_appl_srv_runtime~execute_action
```

현재 골격의 목적은 실제 PO 생성이 아니라 아래 검증이다.

| 검증 대상 | 목적 |
|---|---|
| Function Import 진입 | `CreatePoFromRfq` 호출이 `EXECUTE_ACTION`으로 들어오는지 확인 |
| Parameter 수신 | `RfqNo`가 `it_parameter`에서 읽히는지 확인 |
| Return EntitySet | `PoCreateResultSet` 형태로 메시지 반환이 되는지 확인 |

### 6.1 ABAP Component명 주의

`PoCreateResult` Property는 OData Metadata에서 CamelCase로 보인다.

```text
SeqNo
MessageType
MessageText
RfqNo
PoNo
PoItem
RfqItem
MqNo
MqItem
```

하지만 MPC가 생성한 ABAP 구조 컴포넌트명은 underscore 없이 아래처럼 생성된다.

| OData Property | ABAP Component |
|---|---|
| `SeqNo` | `SEQNO` |
| `MessageType` | `MESSAGETYPE` |
| `MessageText` | `MESSAGETEXT` |
| `RfqNo` | `RFQNO` |
| `PoNo` | `PONO` |
| `PoItem` | `POITEM` |
| `RfqItem` | `RFQITEM` |
| `MqNo` | `MQNO` |
| `MqItem` | `MQITEM` |

따라서 ABAP에서는 아래처럼 접근해야 한다.

```abap
ls_result-seqno       = 1.
ls_result-messagetype = 'S'.
ls_result-messagetext = |RFQ { lv_rfq_no } 기준 Function Import 호출이 정상적으로 완료되었습니다.|.
ls_result-rfqno       = lv_rfq_no.
```

## 7. Function Import 테스트 결과

### 7.1 Metadata 확인

`$metadata`에는 Function Import가 정상적으로 표시되었다.

```xml
<FunctionImport Name="CreatePoFromRfq"
  ReturnType="Collection(ZGWD3MM0005_SRV.PoCreateResult)"
  EntitySet="PoCreateResultSet"
  m:HttpMethod="POST">
  <Parameter Name="RfqNo" Type="Edm.String" Mode="In" MaxLength="10"/>
</FunctionImport>
```

즉, 모델 자체는 Metadata에 반영되었다.

### 7.2 Gateway Client 테스트 결과

테스트 RFQ는 현재 시스템에 존재하는 `RQ10000002`를 사용하였다.

| 순서 | Method | URI/Body | 결과 |
|---:|---|---|---|
| 1 | `POST` | `/CreatePoFromRfq?RfqNo='RQ10000002'` | 405 Method Not Allowed |
| 2 | `POST` | `/CreatePoFromRfq?RfqNo='RQ10000002'&$format=json` | 405 Method Not Allowed |
| 3 | `POST` | `/CreatePoFromRfq(RfqNo='RQ10000002')` | 400 Bad Request |
| 4 | `GET` | `/CreatePoFromRfq?RfqNo='RQ10000002'` | 405 Method Not Allowed |

| 6 | `POST` | `/CreatePoFromRfq` + JSON Body `{ "RfqNo": "RQ10000002" }` | 실패 |

`/IWFND/ERROR_LOG`에서 확인한 주요 메시지는 아래와 같다.

| HTTP | Error Text |

### 7.4 Breakpoint 결과

`ZCL_ZGWD3MM0005_DPC_EXT`의 아래 메소드에 External Breakpoint를 걸었다.

```abap
/iwbep/if_mgw_appl_srv_runtime~execute_action
```

그러나 어떤 테스트에서도 Breakpoint가 걸리지 않았다.

즉, 요청이 `DPC_EXT`까지 도달하지 못하고 Gateway Framework의 URI Parser 단계에서 실패하고 있다.

## 8. 현재 판단

현재 문제는 ABAP PO 생성 로직 문제가 아니다.

아직 실제 PO 생성 로직은 구현하지 않았고, Gateway Framework가 Function Import URI/Parameter를 해석하는 단계에서 요청이 차단되고 있다.

| 판단 항목 | 결론 |
|---|---|
| Service Root | 정상 |
| `$metadata` | 정상 |
| Function Import Metadata | 정상 표시 |
| `EXECUTE_ACTION` 진입 | 실패 |
| 실패 위치 | Gateway URI Parser 단계 |
| DPC_EXT 코드 문제 가능성 | 낮음 |
| Function Import 방식 지속 | 비추천 |

따라서 2차 개발 설계서 V1.1.0에서는 Function Import를 계속 사용하지 말고, **EntitySet POST 방식인 `PoCreateRequestSet + CREATE_ENTITY`로 전환**하는 것이 좋다.

## 9. 권장 전환 방식

### 9.1 기존 방식

```text
CreatePoFromRfq Function Import
-> EXECUTE_ACTION
-> 현재 Gateway URI Parser 단계에서 실패
```

### 9.2 전환 방식

```text
PoCreateRequestSet
-> CREATE_ENTITY
-> io_data_provider->read_entry_data
-> Backend에서 RFQ 기준 PO 생성
-> 처리 요약 Entity 1건 반환
```

이 방식은 UI5에서도 자연스럽게 호출할 수 있다.

```javascript
oModel.create("/PoCreateRequestSet", {
  RfqNo: "RQ10000002"
}, {
  success: function (oData) {
    // MessagePopover 표시 및 RFQHeaderSet/RFQItemSet/MQCompareSet 재조회
  },
  error: function (oError) {
    // 시스템 오류 표시
  }
});
```

### 11.2 Header


## 12. 실제 PO 생성 업무 로직은 유지

API 진입 방식만 바뀌고, 실제 업무 로직은 V1.0.0 설계서의 핵심 내용을 유지한다.

### 12.1 입력

| 입력 | 설명 |
|---|---|
| `RfqNo` | 선택 RFQ 번호 |

### 12.2 Backend 처리 대상

Backend가 직접 조회해야 할 데이터:

| 데이터 | 출처 |
|---|---|
| RFQ Header | `ZTD3MM0016`, `BSART = 'RQ'` |
| RFQ Item | `ZTD3MM0017`, RFQ 번호 기준 |
| 채택 MQ Item | `ZTD3MM0017`, `ANFNR/ANFPS`, `SELIDC = 'X'` |
| MQ Header | `ZTD3MM0016`, `BSART = 'MQ'` |
| 기존 PO 참조 | `ZTD3MM0017-QTNFN/QTNFP` |
| PR | `ZTD3MM0015` 또는 현재 프로젝트 PR 테이블 |

### 12.3 PO Header 그룹핑 기준

PO Header는 아래 필드 조합 기준으로 나눈다.

```text
BUKRS + EKORG + EKGRP + LIFNR + ZTERM + WAERS
```

### 12.4 PO 번호 채번

| 항목 | 값 |
|---|---|
| Number Range Object | `ZNRD3MM01` |
| 기본 Interval | `01` |
| 비고 | SAPGUI 구매문서 생성 프로그램과 동일한 번호 오브젝트 사용 |

### 12.5 저장 정책

저장 정책은 All-or-Nothing으로 유지한다.

| 상황 | 처리 |
|---|---|
| 모든 검증 통과 | PO Header/Item INSERT, PR 갱신 |
| 하나라도 오류 | PO 생성 없이 전체 중단 |
| DB/번호채번 오류 | Rollback 후 Gateway Exception 처리 |

## 13. 오류 처리 기준

### 13.1 사용자가 조치 가능한 업무 오류

아래 오류는 UI5 MessagePopover에 표시할 수 있도록 `MessageType = 'E'` 형태의 응답으로 처리한다.

| 오류 | 처리 |
|---|---|
| RFQ 번호 누락 | `MessageType = 'E'` |
| 존재하지 않는 RFQ | `MessageType = 'E'` |
| 미채택 RFQ Item 존재 | `MessageType = 'E'` |
| 미응답 MQ | `MessageType = 'E'` |
| 수량/단가/가격단위 오류 | `MessageType = 'E'` |
| 납기일 누락/과거 | `MessageType = 'E'` |
| 이미 PO 생성된 MQ | `MessageType = 'E'` |

### 13.2 시스템/기술 오류

아래 오류는 사용자가 화면에서 직접 해결하기 어렵기 때문에 Rollback 후 Gateway Exception 처리를 고려한다.

| 오류 | 처리 |
|---|---|
| Number Range 실패 | Business/Tech Exception |
| DB INSERT 실패 | Rollback + Business Exception |
| DB UPDATE 실패 | Rollback + Business Exception |
| Runtime 예외 | Tech Exception |

## 14. 기존 Function Import 처리 방침

기존에 만든 아래 객체들은 당장 삭제하지 않는다.

| 객체 | 처리 방침 |
|---|---|
| `PoCreateResult` | 당장 유지 |
| `PoCreateResultSet` | 당장 유지 |
| `CreatePoFromRfq` | 당장 미사용 상태로 유지 |
| `EXECUTE_ACTION` 재정의 | 향후 정리 가능 |

이유:

- 이미 Runtime Generate가 완료되어 있으므로 즉시 삭제하면 영향 범위를 다시 검토해야 한다.
- V1.1.0에서 `PoCreateRequestSet` 방식이 정상 동작하는 것을 먼저 확인하는 것이 안전하다.
- 최종 정리 단계에서 미사용 Function Import와 Result Entity를 삭제할지 결정한다.

3. Property 추가
4. Runtime Generate
5. `DPC_EXT`에서 `POCREATEREQUESTSET_CREATE_ENTITY` 재정의

### 15.3 기본 골격 테스트

초기에는 실제 PO 생성 없이 아래만 구현한다.

```abap
io_data_provider->read_entry_data(
  IMPORTING
    es_data = ls_request
).
```

그리고 `RfqNo`를 다시 응답으로 반환한다.

### 15.4 실제 PO 생성 구현

## 16. 주의사항

### 16.1 ABAP SELECT 작성

프로젝트 지침상 아래 규칙을 유지한다.

| 규칙 | 내용 |
|---|---|
| `SELECT *` 지양 | 필요한 필드를 `FIELDS`에 명시 |
| `SELECT ... ENDSELECT` 금지 | 반드시 Internal Table 조회 |
| LOOP 안 SELECT 금지 | 선조회 후 Internal Table 처리 |
| New Open SQL 사용 | `SELECT FROM ... FIELDS ... INTO ...` 형태 |

### 16.2 UI5 디자인

프로젝트 지침상 CSS 추가는 최대한 피한다.

PO 생성 버튼과 결과 메시지는 기존 UI5 패턴을 따른다.

| 영역 | 기준 |
|---|---|
| 버튼 | 기존 Footer 버튼 패턴 재사용 |
| 메시지 | 기존 `processMessages` 모델 + `sap.m.MessagePopover` 재사용 |
| 성공 후 갱신 | 기존 Header/Item/MQ refresh 로직 재사용 |

### 16.3 Function Import에 더 시간을 쓰지 말 것

현재 Function Import는 Metadata에는 보이지만, Gateway URI Parser 단계에서 실패한다.

External Breakpoint가 `EXECUTE_ACTION`에 걸리지 않는 것이 핵심 근거다.

따라서 학원에서는 Function Import 문제를 더 추적하기보다, `PoCreateRequestSet + CREATE_ENTITY` 방식으로 빠르게 전환해서 2차 개발을 이어가는 것이 좋다.
